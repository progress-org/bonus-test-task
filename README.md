# **Тестовое задание: Backend (Node.js + TypeScript)**

Репозиторий содержит решение тестового задания по рефакторингу и доработке системы бонусных баллов.

Основной упор в решении сделан на обеспечение строгой консистентности данных (ACID), защиту от гонок (race conditions) при конкурентных запросах, реализацию механизма идемпотентности и надежную фоновую обработку задач через очередь.


## **🛠 Стек технологий**

- Node.js & TypeScript

- Express

- PostgreSQL & Sequelize

- BullMQ & Redis

- Jest & Supertest (для интеграционного тестирования)

- Docker & Docker Compose


## **🚀 Запуск проекта**

1. Склонируйте репозиторий и перейдите в папку проекта.

2. Поднимите инфраструктуру и приложение с помощью Docker Compose:\
   docker compose up -d --build

3. Приложение будет доступно на порту 5000 (или другом, указанном в .env). Накатывание миграций происходит автоматически (или выполните команду миграции, если это предусмотрено вашим package.json).


## **🧪 Запуск тестов**

В проекте реализованы интеграционные тесты (Jest + Supertest), покрывающие все критические сценарии из ТЗ (идемпотентность, гонки, сгорание бонусов, защита от дублей в очереди).

Для запуска тестов в изолированном окружении внутри запущенного Docker-контейнера выполните:

docker compose exec api npm test

_(Тесты используют базу данных в памяти или изолированную схему и выполняются последовательно благодаря флагу --runInBand и явному закрытию всех соединений)._


## **📝 Анализ и рефакторинг (Обязательная часть)**

В рамках выполнения задания был проведен рефакторинг логики начисления и списания бонусов. Ниже приведены ответы на ключевые вопросы по реализации:


### **1. Какие проблемы были в исходной реализации списания?**

В исходной («наивной») реализации полностью отсутствовала транзакционность и защита от конкурентного доступа. Баланс пользователя высчитывался динамически агрегацией всех его транзакций, однако это происходило _до_ фактического обновления базы. При одновременных запросах (Race Conditions) система читала один и тот же устаревший баланс, что приводило к двойному списанию и уходу баланса в отрицательную зону. Кроме того, при расчете не учитывались просроченные (сгоревшие) начисления.


### **2. Какие проблемы при одновременных запросах вы устранили и как именно?**

Была устранена критическая проблема ухода баланса в минус (Negative Balance) при параллельных запросах POST /users/:id/spend.

Решение реализовано за счет **Row-Level Locking** (блокировки строк на уровне БД) с использованием SELECT ... FOR UPDATE (в Sequelize реализовано через опцию lock: transaction.LOCK.UPDATE). Теперь параллельные транзакции выстраиваются в строгую очередь: пока первый запрос не завершит чтение, валидацию и списание, второй запрос находится в состоянии ожидания, а затем читает уже обновленные данные.


### **3. Какие обязательные правила корректности вы обеспечили на уровне БД и на уровне кода?**

**На уровне БД:**

- Заменен глобальный уникальный индекс request\_id на составной уникальный индекс (user\_id, request\_id) (миграция 003).

- Введена колонка remainder (остаток) для записей типа accrual, чтобы избежать сложных агрегаций при частичных списаниях и безопасно применять построчные блокировки.

**На уровне кода:**

- Вся логика валидации и изменения данных обернута в строгие транзакции (sequelize.transaction).

- Добавлена обработка ошибок нарушения уникальности (SequelizeUniqueConstraintError) для случаев, когда параллельный запрос с тем же requestId фиксируется в БД на миллисекунду раньше текущего.


### **4. Как реализована защита от повторного одинакового запроса (duplicate request)?**

Внедрен механизм идемпотентности, привязанный к паре (user\_id, requestId).

Внутри транзакции, до применения блокировок на баланс, происходит поиск существующих списаний по заданному request\_id.

- Если списание найдено и запрошенная сумма (amount) **совпадает** с ранее списанной — API возвращает 200 OK с флагом { success: true, duplicated: true }.

- Если суммы **отличаются** — API отклоняет запрос со статусом 409 Conflict, защищая систему от перезаписи payload'а.


### **5. Как обеспечено, что просроченное начисление (expired accrual) не участвует в балансе?**

В методы getUserBalance и логику выборки начислений для списания (executeSpend) внедрены строгие фильтры на уровне SQL-запроса: \[Op.or]: \[{ expires\_at: null }, { expires\_at: { \[Op.gt]: new Date() } }]. Таким образом, просроченные записи просто не блокируются и не учитываются при расчете доступного remainder.


### **6. Как реализована надежная обработка очереди (повторные попытки, паузы, защита от дублей)?**

Обработка очереди реализована через **BullMQ**:

- **Предсказуемый jobId:** При постановке задачи (endpoint POST /jobs/expire-accruals) ей присваивается жесткий jobId: 'expire-accruals'. Это гарантирует, что задача не будет дублироваться в очереди при множественных вызовах эндпоинта.

- **Надежность:** Настроен механизм retry (3 попытки) с экспоненциальной задержкой (exponential backoff, минимум 1000мс).

- **Защита от бизнес-дублей:** Worker перебирает просроченные начисления и инициирует их списание (обнуление remainder), генерируя уникальный предсказуемый ключ: request\_id = "expire:\<accrual\_id>". Эта операция проходит через общую транзакционную логику. Если задача упадает и будет запущена повторно, транзакция с таким ключом уже будет существовать, и Worker просто проигнорирует её, исключив двойное бизнес-влияние.


### **7. Какие компромиссы вы приняли в рамках ограничения 4–6 часов?**

Для обеспечения надежности в условиях ограниченного времени был выбран компромисс в модели данных — **добавление колонки remainder (остаток)** прямо в таблицу транзакций bonus\_transactions (через новую миграцию).

В идеальной Event Sourcing архитектуре таблица транзакций должна быть строго append-only (неизменяемой), а актуальные балансы должны рассчитываться на лету или храниться в отдельной таблице агрегированных снапшотов (balances / wallets).

Однако, в условиях тестового задания, добавление remainder — это самый элегантный, безопасный и производительный способ реализовать точечный Row-Level Lock на конкретные начисления без необходимости блокировать всю таблицу пользователя при каждом списании.
